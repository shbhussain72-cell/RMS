### A. ⚠️ Real bug — a merged request stamped ONE from/to pair across every member
User-reported from their own screenshot: a "Switch to a different city · 3 members" request read `Delhi → Hyderabad`, but Mohammed Husain (`m4`) was in **Colombo**, not Delhi. **Both** ends of the route turned out to be unsafe to collapse:
- **Origin.** `handleConfirmed()` (`HostCityMove.tsx`) built `fromLabel` from `currentCityName`/`currentZoneName` — the screen's single **representative** `groupIndex` allocation. Since `ac3515c`/the merged "Switch to a different city" option, one request can cover groups sitting in **different** cities (`groupIndices: number[]`), so every member after the first group was misreported. The table's CURRENT column already knew this (`currentAllocFor(gi)`, added with the comment "must read PER ROW now that … can merge groups from different origin cities") — `handleConfirmed` was simply never updated to match.
- **Destination.** `toLabel` read `a0` — the *first* staged member's `assign[]` entry. But `assign[id]` is written when that member is staged, against whatever destination was active at that moment, so changing the picked city part-way through a selection leaves earlier members staged to the earlier city. Every member staged after the switch was misreported. (This is the likelier explanation for the reported card showing `Hyderabad` when the user believed they'd picked Colombo.)
- Fix: `ChangeRequest` gains `members?: { id; name; fromLabel; toLabel }[]` — the authoritative per-member record. Origins come from walking `groupIndices` and reusing `currentAllocFor(gi)`; destinations from each member's own `assign[]` entry. The flat `fromLabel`/`toLabel` are kept (now the first member's, documented as representative) so older persisted requests and `useAskHelpChat.ts`'s two call sites still work — `RequestCard` falls back to them when `members` is absent, which is accurate for those since they never merge groups.
- Reproduced and verified all three shapes by seeding `flow.changeRequests` directly: **one route** (`Delhi → Colombo` ×3) → hero route; **shared destination, mixed origins** → "MOVING TO Colombo" + `3 members · from 2 cities`, Mohammed Husain correctly under his own `Colombo →` route; **mixed both** → "REQUESTED CHANGES" + `3 members · 2 destinations`, one route block each.
- ⚠️ **Then verified the PRODUCER end-to-end**, which the seeding above does NOT exercise (it writes `members` directly, bypassing `handleConfirmed` entirely — the user reported the bug again after the first fix, from a request that predated it). Real path: seed `[m1+m3]=Delhi, [m4]=Colombo` + `stageOverrides['ashara-1448']='zone_closed'` (→ `windowOpen: false`, so the move files a request instead of applying), then Modify Reservation → "Switch to a different city · 3 members" → Hyderabad → "Request all" → "Submit request(3)" → "Submit Request". The stored request now correctly reads `m4.fromLabel: "Colombo"`. The HostCityMove table itself was always right (`CURRENT: Host City Colombo → NEW: Hyderabad`) — only `handleConfirmed`'s snapshot was wrong.

### C. One card PER GROUP + partial cancel — a merged request was un-withdrawable in part
⚠️ User: *"if he wanted to cancel request for Mohammed Husain how will user do that — so give a separate card"*. A merged request covering several groups rendered as ONE card whose only control was a Cancel that took **the entire request** down. There was no way to withdraw one group.
- **Store**: `cancelChangeRequest(id)` **replaced** by `cancelChangeRequestMembers(id, memberIds)` — filters `memberIds`/`memberNames` **by index** (parallel arrays; filtering names by value would desync on duplicate names) plus `members`, and drops the request entirely once nothing remains. Cancelling a whole request is now just "pass all its memberIds". The old whole-request action had no call sites left and was deleted rather than left as a footgun.
- **`ManageReservations`**: new `requestSlices` splits every pending request into one slice **per group** (`rawGroups.findIndex`), each rendered as its own `RequestCard`. **The group is the smallest safe unit** — a guardian and dependent reserve together and must never be split, which `buildAllGroups` already encodes. Members whose group can't be resolved fall back to bucketing by route, so nothing is silently dropped. `RequestCard` now takes a `RequestSlice` (not a `ChangeRequest`) and cancels only that slice's members; `RequestsSummaryCard`'s count and the popup's filter chips count **slices**, so "2 pending requests" matches the 2 cards on screen.
- Slices of a larger request show `Cancels these N members only` in the footer, so the per-card Cancel can't be misread as taking down the members on the sibling cards. The line disappears once a request has only one group left.
- Verified end-to-end: 1 merged request over 2 groups → summary reads "2 pending requests", 2 cards (`Delhi → Hyderabad` ×2 members, `Colombo → Hyderabad` ×1). Cancelling Mohammed Husain's card leaves `memberIds: ['m1','m3']` intact and the surviving card drops its "only" line; cancelling the last card empties `changeRequests` and auto-closes the popup. **Downstream check**: back in `HostCityMove`, Murtaza + Syed Nazia still show the "Pending approval" badge while Mohammed Husain returns to `CURRENT: Colombo → NEW: Choose city` — i.e. `isPendingMember` correctly frees only the withdrawn member. Zero overflow at 390px (both cards 358px) and 1280px.

### E2. ⚠️ Pre-existing bug found while wiring E — every CURRENT cell read one group off
Found by inspection while adding `indexMap`, then reproduced: the tables/cards key rows by position within `groups` (`groupIndices.map(...)` — the subset this screen moves), but `flow.groupCities`/`groupZones`, and therefore `currentAllocFor`, are keyed by position in the FULL `allGroups` array. **They only coincide when `groupIndices` is `[0,1,2,…]`**, which is why it had gone unnoticed.
- Repro: `g0=Delhi (+zone)`, `g1=Kolkata`, `g2=Colombo`. The zone on g0 routes it to the combined city+zone card, so the plain "Switch to a different city" card covers only `groupIndices: [1,2]`. Before the fix the table showed Sakina (g1, Kolkata) as **Delhi** and Mohammed Husain (g2, Colombo) as **Kolkata** — every row shifted by one.
- Fix: `currentAllocForRow(li) = currentAllocFor(groupIndices[li] ?? li)`, used by all four row-level call sites (desktop table, mobile cards, and both new requested views). `handleConfirmed`'s own call is left alone — it iterates `groupIndices` directly, so it already holds real indices. Verified: Kolkata and Colombo now render correctly, in both the movable and requested tables.
- Convention going forward: inside this screen, row/local indices key `groups[...]` (`toggleGroupMove`, `onChooseDest`); anything reading `flow.groupCities`/`groupZones` must translate through `groupIndices` first.

### H2. ⚠️ Real bug — a staged zone survived its city being removed (`CitySelection.tsx`, `7f6b65b`)
User: *"why the inside dropdown saying Zone A - Main Hall? i didn't even select a zone"* — a row whose city button still read "Select Delhi" was showing a zone beside it.
- Root cause: `groupZoneMap` was only ever written, never pruned. Removing a group's city (or switching it to a different one) left the staged zone behind, so an unreserved row kept displaying a zone that had been picked under a previous city. The pale styling was just the picker's `disabled={!isAssigned}` state, which made it read as inert decoration rather than wrong data.
- Reproduced: stage a zone → "Remove all" → the row reads `Select Mumbai` and still shows `Zone C - West Wing`.
- Fix: **one `useEffect` keyed on `groupCityMap`** prunes any entry whose group has no city, or whose zone isn't in that city's own zone list. Deliberately centralised rather than patched at each mutation site (row toggle, Select all / Remove all, swap-all, city switch) — there are too many for a per-site fix to stay correct. Returns the previous Map unchanged when nothing was pruned, so it can't loop.
- Membership is the validity test (not a `cityId` field, which seed's `Zone` doesn't carry). Safe because seed zone ids are namespaced per city — `zonesByCityId` builds them via `genZones(\`z-${c.id}\`, 22)` — so a Mumbai zone id can never appear in Delhi's list, making a city SWITCH invalidate correctly too, not just a removal.
- ⚠️ Distinct from the "NOW Colombo · Zone A - Main Hall" pill on the same row, which is the persisted CURRENT allocation and correctly survives — don't "fix" that one to match.

### Gotcha: CSS shine/glow effect, two failed attempts before it worked
Building the `.reserve-all-glow` shine took three passes:
1. First attempt used `inset: 0 -20% 0 -20%` **together with** `width: 40%` on the same element — an invalid/over-constrained combo (inset's left+right conflict with an explicit width) — plus animated `transform: translateX() skewX()` as one compound value. Result: the shine broke out of the rounded pill as a hard-edged rectangle.
2. Second attempt removed the skew entirely (straight vertical band) to get it contained — worked, but lost the diagonal "light reflection" look the user actually wanted.
3. Final fix: keep the ~20° skew, but make it a **static** `transform: skewX(-20deg)` on the pseudo-element (not animated), and animate only the `left` position via `@keyframes` instead of combining `translateX()` + `skewX()` in one animated transform. A static transform composes cleanly with the parent's `overflow: hidden` — confirmed via computed styles (`matrix(1, 0, -0.36397, 1, 0, 0)` = skewX(-20deg), constant across the sweep) that it now stays cleanly clipped to the pill on both breakpoints.

### Preview/testing gotchas (this session)
- **`navigate` with `force: true` can silently reset the Browser pane viewport** back to its ~549×550 default even after an explicit `resize_window` call earlier in the session — always re-check `window.innerWidth` (or just re-call `resize_window`) after a forced navigate before asserting on desktop-vs-mobile layout, otherwise you'll be reading the wrong breakpoint's DOM.
- **`read_console_messages` accumulates history across reloads/navigations within the same tab** — a genuinely-fixed error from three edits ago can still show up on a later check in the *same* tab. Open a **fresh tab** (`tabs_create` → navigate → `read_console_messages` → `tabs_close`) whenever you need a trustworthy "is this actually broken right now" answer.
- Old localStorage-persisted `flow.questionnaire` objects predate new fields like `airportPickupNeeded`/`emergencyAltMobile` — they come back as `undefined`, not `null`. A naive `value !== null` "is answered" check reads `undefined` as answered (bug); check `v == null` (loose) to catch both. Same idea applies to any future new field added to a persisted store shape.

### Flow (current)
- **Ask Help lands in the chat first.** A card's `Ask Help` CTA (`useCard`'s `ended` branch → `handleCardAskHelp` = `setAskHelp`, `MiqaatList.tsx`) opens the contextual chat; the general floater (`AskHelpDock`) opens the open-ended chat. **The chat is a router**: `category → event → handoff-preview → handoff`. ## Architecture notes / gotchas

1. **One active `flow` + a per-miqaat archive (`registrations`).** `flow` is the journey currently being *edited* (its `miqaatId` names the active event); `store.registrations` holds a saved journey for every *other* registered event, so several events stay registered at once and all render side-by-side in Home's "Registered" section. Invariant: the active `flow`'s miqaat is **not** in `registrations` — `setActiveMiqaat(id)` archives the outgoing journey and loads/creates the target, which is what makes switching between events non-destructive. To read a specific event's state (active *or* archived) use `journeyFor(flow, registrations, id)` — MiqaatList and MiqaatDetail do this per card. Editing screens (AddPeople/City/Zone/Manage) call `setActiveMiqaat(id)` on mount, and Home cards / detail CTAs switch **before** navigating so the next screen edits the right event. `deriveStatus` still returns seed status for any journey it doesn't own (empty `journeyFor` result).
2. **Header transform → portal your modals.** The sticky header applies an inline `transform`, making it a containing block for `position: fixed` descendants. `InvitationPopup`, `InvitationBanner`, and `MiqaatList`'s `InviteToast` all `createPortal` to `document.body`. Do the same for any new fixed overlay.
3. **One-shot Home banner + StrictMode.** The invitation banner arms off `flow.invitationBannerPending` and consumes it in an effect. It renders correctly on **SPA navigation** to Home (the real flow: register → tap Home); a hard `location.reload()` can appear to swallow it in dev StrictMode — that's a test artifact, not a bug.
4. **City Selection starts in the queue loader** (`queue-waiting` → `queue-active` → `browse`). Both `sameDayFlow` and normal flows land here; `QueueActive` auto-advances after ~5s.
5. **Mobile vs desktop layout split.** Most flow screens render a mobile block and a separate desktop block; a few use one shared layout with `sm:` responsive classes. Home cards (`RegisteredCard`, `UpcomingRow`) are single shared layouts with `sm:` overrides — the `wide` / hug-CTA behaviour is web-only (`sm:`), mobile keeps stacked full-width buttons.
6. **Working tree is clean as of `9a37c62`** — nothing in-progress/uncommitted. Not pushed to a remote. Review any session's commits with `git show <hash>`.
7. **Screenshots are unreliable** in this preview env (they've timed out; treat any success as a bonus, not a dependency) — verify via `read_page` / `getComputedStyle` / `getBoundingClientRect` / class names instead, and drive the app with `javascript_tool` (`localStorage['miqaat-flow']` holds `{state:{flow, registrations, reopenRequests, …}}`).
8. **Two similar-looking but distinct "pending approval" mechanisms — don't conflate them.** `flow.changeRequests` (`ChangeRequest`, per-journey) is for changing an **already-complete** city/zone allocation (raised from `HostCityMove.tsx`, shown/cancelled on `ManageReservations.tsx`). `reopenRequests` (`ReopenRequest`, top-level in the store, keyed by miqaat id) is for **unlocking a missed window** (register/city/zone) that closed before the user acted at all (raised from Home cards, shown in the new "Requested" section). Neither has a real backend — `ChangeRequest` only supports cancel; `ReopenRequest` has a demo-only `approveReopenRequest` triggered by tapping the Requested card.
9. **If an automated test says a toast "isn't showing," measure elapsed time before concluding it's broken.** Toasts in this app auto-dismiss after ~2.8–3s; a multi-step tool-driven test (reset state → navigate → click → wait → check) can easily burn more than that in round-trips alone, making a perfectly working toast look absent. Use a `MutationObserver` with `performance.now()` timestamps if you need to prove timing rather than trusting a single delayed check.
