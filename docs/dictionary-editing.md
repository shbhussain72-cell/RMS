# The dictionary editor, the spreadsheet, and how an edit stops being an edit

Three layers, in one direction. Nothing in this document, and nothing in the code it describes,
authors a Lisan al-Dawat value.

    reviewer types a value  →  shared store (a revision, append-only)
                            →  the .xlsx, cell-level, by the sync
                            →  lsd.json, regenerated by the build from the committed .xlsx

The **committed .xlsx is the source of truth** and `src/i18n/lsd.json` is generated from it. An
override is a proposal held in front of the sheet. The production build reads the committed
wordlist and never the live store.

---

## 1. Override retirement

An override is **merged** once its value is already in the committed wordlist, and a merged
override must stop being applied and stop being counted.

    isMerged(rev)  ⇔  bakedValue(rev.value) === bakedValue(baselineValue(rev.key))

Two things in that line are load-bearing, and both fail silently if you get them wrong.

### The comparison must go through `bakedValue`

The generator gives mixed-script values an explicit base direction: the store's `register كرو`
is `‏register كرو` — with a leading U+200F — in `lsd.json`. Those two strings are not equal.

A retirement check written against the raw value therefore never matches. Nothing ever retires,
the pending count climbs forever, and every one of those "pending" edits is already in the
wordlist. It looks exactly like the feature working, which is why it gets to survive.

### The baseline must come from the generated payload, not from `ENTRIES`

`ENTRIES` is what the app is rendering right now, and `applySharedOverrides` writes into it. Read
the baseline from there and you compare an override against itself: everything retires the instant
it is applied, and every real pending edit disappears from the count. The opposite failure, equally
quiet. `baselineValue()` reads `lastPayload` for this reason and there is a comment on it saying so.

### Merged overrides are not applied at all

Applying one changes nothing visible — the value already equals the baseline — so it is tempting
to leave it in the map. Doing that keeps the entry marked `staged: true`, and the editor's
**"edited" badge reads `staged`**. A row that went into the wordlist a month ago would go on
announcing itself as an unsaved edit.

That badge is [assertion-discipline.md](assertion-discipline.md)'s fifth class: a true statement
that a later change makes false, with nothing that fails. The defence is not a test on the badge;
it is that the badge cannot be fed a value that contradicts it, because merged overrides never
reach the dictionary. Revision history is kept — retirement is about what is *applied* and
*counted*, never about what is *recorded*.

## 2. What the spreadsheet actually contains

Measured from `RMS_Mumineen_LSD_wordlist_v4.xlsx` at 1085 data rows, not assumed. Everything here
constrains how the sync is allowed to write.

### `F370` = 1448 — debris, and it stays

One numeric cell, in an otherwise empty column, on one row. It is **not** a header for an intended
column, and the evidence is not a judgement call:

- It is the **only** cell outside `A:C` in the whole sheet.
- Row 1 — the header row — has no D/E/F cell at all. `spans="1:3"`. A column somebody meant to
  use would have been given a name.
- Its number format is `General` (`numFmtId="0"`), so it is the integer 1448 and not a date. As a
  date serial it would be 1903-12-19.
- The `Read me` sheet dates the wordlist itself: *"rebuilt after training on the 1448H Iqtibasat
  (53 pages)"*. 1448 is the Hijri year. Somebody typed the year into a stray cell beside row 370
  (`Status Tracking`) and moved on.
- The widened `spans="1:6"` hint covers rows 369–384 — one contiguous editing session around that
  row, with a value left behind in exactly one of them.

**Verdict: debris.** It is preserved anyway, because cell-level editing preserves everything it
does not address, and because "probably debris" is not a licence to delete a number from someone
else's spreadsheet.

### Nothing depends on row positions — but only just

- **Formulas: none.** Zero `<f>` elements across both sheets.
- **Named ranges: one**, and it is stale already — `_xlnm._FilterDatabase` = `'Word List'!$A$1:$C$543`,
  hidden, left behind by an autofilter applied when the sheet was half its present length. There is
  no `<autoFilter>` element on the sheet any more. Appending cannot make it worse; it has been
  wrong since the sheet passed row 543. Leave it alone.
- **No merged cells, no data validation, no conditional formatting, no tables, no pivots, no
  hyperlinks.**
- **The `Read me` sheet cites row numbers in prose** — "Row 231", "Row 230", "Rows 457, 500",
  "Row 312", under *ASSUMPTIONS — reject any of these*. These are human references into the Word
  List, and they are the reason the placement rule matters.

So **appending at the end is purely additive** and there is nothing downstream to update.
**Inserting or sorting rows is not**: it would silently invalidate four citations in a document
whose whole purpose is to record which translations are open to challenge. The sync appends. It
never inserts, never sorts, never reorders.

### Five English cells carry a `۞` ornament

Rows 2, 3, 4, 10 and 11 — the Login block; `۞` is a real glyph in the app's own Login divider, so
it travels with copy/paste. `normKey` strips it, which means **a store key never equals the raw
cell text for those rows**.

A sync that indexes rows by the raw cell finds no match, decides the key is new, and appends a
duplicate row for a string that already has one. `src/i18n/wordlistNorm.test.ts` asserts this
against the real sheet: that the ornamented rows exist at all (a control — the suite goes vacuous
if someone hand-cleans them), that the store key never equals the raw cell, that a raw-keyed index
misses exactly those rows while a `normKey`-keyed index finds them, and that no wordlist consumer
strips ornaments with a rule of its own.

### The sync must patch the XML, not rewrite the workbook

Measured, by round-tripping the real file through SheetJS `read` → `write`:

| | survives a SheetJS round trip |
|---|---|
| `F370` (the 1448) | yes |
| `_xlnm._FilterDatabase` | yes |
| RTL sheet view, column widths, dimension | yes |
| **the Kanz-al-Lulu font on every cell** | **no — `styles.xml` comes back with Calibri alone** |
| **shared strings** | **no — `sharedStrings.xml` is dropped; cells become inline `t="str"`** |

The `Read me` sheet's last line is *"Column C is Kanz-al-Lulu 14pt, right-aligned, RTL reading
order."* A SheetJS write silently deletes that from all 1085 rows. Every value would still be
correct, every assertion about values would still pass, and the LSD column would render in a
fallback face.

**So the sync edits `xl/worksheets/sheet1.xml` and `xl/sharedStrings.xml` inside the zip and leaves
every other part byte-identical.** That is what "cell-level" has to mean here — not "call SheetJS
and only touch column C", which is what it sounds like and is not the same thing.

## 3. What never changes

- `src/i18n/lsd.json` is **generated**. Never hand-edited, never written by an API.
- Sentinel values (`remove`) are not editable and are never sync candidates — a sentinel is an
  instruction about a string, not a translation of it.
- Mojibake rows stay read-only; legacy-font paste (ثث سس طط ضض صص ظظ) is refused at the input and
  refused again server-side at 422.
- Class B2 loanword identity values are marked "no action needed", not offered for editing.
- Tool chrome is English, carries `SCANNER_IGNORE_ATTR`, and goes through `t()`/`tx()`.
- **You never author Lisan al-Dawat.** The editor stores exactly the characters a human typed, or
  refuses them.
